# Propósito

**Retrieval-Augmented Generation (RAG)** separa el conocimiento recuperable de la capacidad generativa del modelo. Antes de pedir una respuesta al LLM, el sistema busca evidencia relevante en una fuente externa, selecciona el contexto útil y lo incorpora a la solicitud de generación.

El patrón resulta especialmente útil cuando el conocimiento necesario cambia con más frecuencia que el modelo, pertenece a un dominio privado o debe poder rastrearse hasta fuentes concretas.

## El problema

Un modelo generativo puede producir respuestas lingüísticamente plausibles aunque la información necesaria no esté disponible, esté desactualizada o quede fuera del conocimiento aprendido durante el entrenamiento. Añadir todo el corpus al prompt tampoco escala: aumenta el coste, introduce ruido y empeora la selección de evidencia.

El sistema necesita resolver cuatro fuerzas a la vez:

1. **actualización:** incorporar información nueva sin reentrenar el modelo;
2. **selección:** localizar únicamente el material relevante para la consulta;
3. **fundamentación:** condicionar la generación a evidencia explícita;
4. **trazabilidad:** conservar qué documentos influyeron en la respuesta.

## La solución

Introduce una etapa de recuperación antes de la generación:

```text
Consulta
   |
   v
+-------------+
| Retrieval   |
+------+------+ 
       |
       v
+-------------+
| Ranking     |
+------+------+ 
       |
       v
+-------------+
| Context     |
| Builder     |
+------+------+ 
       |
       v
+-------------+
| LLM         |
+------+------+ 
       |
       v
Respuesta + evidencia
```

La recuperación obtiene candidatos, el ranking prioriza los más útiles, el constructor de contexto prepara el material y el LLM genera una respuesta condicionada por esa evidencia.

## Estructura y participantes

- **Consulta:** necesidad expresada por el usuario o por otro componente.
- **Retriever:** busca candidatos en documentos, índices, bases vectoriales, grafos u otras fuentes.
- **Ranker/Re-ranker:** ordena candidatos según relevancia para la consulta.
- **Context Builder:** limita, estructura y etiqueta la evidencia antes de enviarla al modelo.
- **Generator:** produce la respuesta utilizando la consulta y el contexto recuperado.
- **Evidence Trace:** conserva identificadores, scores y procedencia para auditoría y citación.

## Flujo de ejecución

1. Normalizar la consulta.
2. Recuperar un conjunto de documentos candidatos.
3. Ordenarlos o re-rankearlos.
4. Seleccionar el `top-k` compatible con el presupuesto de contexto.
5. Construir un prompt que diferencie instrucciones, pregunta y evidencia.
6. Generar la respuesta.
7. Asociar la respuesta a los documentos utilizados.
8. Evaluar cobertura, atribución y calidad de la recuperación.

## Pseudocódigo

```text
function answerWithRAG(question):
    candidates = retriever.search(question)
    ranked = rank(question, candidates)
    evidence = selectTopK(ranked, contextBudget)

    if evidence is empty:
        return abstainOrFallback()

    context = buildContext(evidence)
    answer = generator.generate(question, context)

    return {
        answer,
        evidence
    }
```

## Caso de uso

Una universidad quiere un asistente que responda dudas sobre normativa académica interna. El reglamento cambia varias veces al año y no debe depender del conocimiento paramétrico del modelo.

El sistema indexa las versiones vigentes, recupera los artículos relevantes ante cada pregunta y obliga al generador a responder a partir del contexto seleccionado. La salida conserva los documentos utilizados para poder mostrar la fuente y auditar la respuesta.

**Criterios de éxito:** la evidencia correcta aparece entre los resultados recuperados, la respuesta no contradice el material proporcionado y las afirmaciones relevantes pueden atribuirse a una fuente recuperada.

## Cuándo utilizarlo

- El conocimiento cambia con frecuencia.
- La información es privada o específica de una organización.
- Se necesita trazabilidad documental.
- El corpus es demasiado grande para introducirlo completo en el contexto.
- Se quiere desacoplar actualización de conocimiento y actualización del modelo.

## Cuándo NO utilizarlo

- La tarea no depende de conocimiento externo y puede resolverse de forma determinista.
- El corpus carece de calidad o de control de versiones.
- La latencia adicional de retrieval no es aceptable y no existe una estrategia de caché o precálculo.
- La aplicación necesita ejecutar acciones, pero se intenta usar RAG como sustituto de autorización o validación de herramientas.

## Ventajas

- Actualiza conocimiento sin reentrenar el modelo.
- Reduce el contexto enviado frente a cargar colecciones completas.
- Permite conservar procedencia y construir citas.
- Facilita separar la capa de conocimiento de la capa generativa.
- Puede combinar fuentes heterogéneas y políticas de ranking diferentes.

## Trade-offs

- Añade latencia y componentes operativos.
- Un fallo de retrieval puede producir una respuesta incorrecta aunque el generador funcione bien.
- La similitud no equivale a relevancia factual.
- El chunking, ranking y presupuesto de contexto pasan a ser decisiones de arquitectura.
- Los documentos recuperados deben tratarse como datos no confiables cuando proceden de fuentes externas.

## Failure modes

| Fallo | Síntoma | Mitigación |
|---|---|---|
| Retrieval miss | La fuente correcta no aparece en el `top-k` | Mejorar indexación, query rewriting, hybrid retrieval y evaluación de recall |
| Context poisoning | Un documento recuperado contiene instrucciones maliciosas | Separar instrucciones de datos y aplicar Tool/Context Output Sanitization |
| Context overload | Demasiados fragmentos degradan la respuesta | Re-ranking, deduplicación y Contextual Compression |
| Stale evidence | Se recupera documentación obsoleta | Versionado, filtros temporales y metadatos de vigencia |
| Unsupported answer | El modelo añade afirmaciones no presentes en la evidencia | Grounding checks, abstención y verificación de atribución |
| Citation mismatch | La cita no respalda la afirmación | Evaluar entailment y cobertura de citas por afirmación |

## Seguridad

RAG amplía la superficie de entrada del sistema. Un documento recuperado puede contener texto que parezca una instrucción para el modelo. Por ello, la evidencia debe tratarse como **datos**, no como autoridad de control.

Controles recomendados:

- etiquetar procedencia y nivel de confianza;
- aislar las instrucciones del sistema del contenido recuperado;
- sanitizar contenido externo antes de incorporarlo al contexto;
- filtrar por permisos antes de recuperar información multi-tenant;
- impedir que el retriever omita las políticas de autorización del dominio;
- registrar qué evidencia fue entregada al modelo.

Patrones especialmente relevantes: **Prompt Injection Defense (69)**, **Access Control (72)** y **Tool-Output Sanitization (100)**.

## Observabilidad

Métricas mínimas recomendadas:

- `retrieval_latency_ms`;
- número de candidatos recuperados;
- `top_k` efectivo;
- distribución de scores;
- documentos/chunks seleccionados;
- tokens de contexto recuperado;
- tasa de consultas sin evidencia;
- tasa de abstención;
- cobertura de citas;
- coste y latencia del generador.

Las trazas deberían permitir reconstruir: consulta -> candidatos -> ranking -> contexto final -> respuesta.

## Coste y latencia

El coste depende de cuatro bloques: recuperación, re-ranking, tamaño del contexto y generación. El patrón no garantiza por sí solo una reducción porcentual universal de tokens o de coste. Es necesario medirlo frente a una baseline representativa.

Para optimizarlo pueden combinarse **Semantic Cache (48)**, **Prompt Compression (49)**, **Contextual Compression (66)** y políticas de `top-k` adaptativas.

## Evaluación

RAG debe evaluarse por capas; medir únicamente la calidad final oculta la causa de los fallos.

### Retrieval

- Recall@k
- Precision@k
- MRR / nDCG cuando exista ground truth de ranking

### Generación

- corrección respecto a la evidencia;
- cobertura de la respuesta;
- tasa de afirmaciones no soportadas;
- calidad de citación/atribución.

### Sistema

- latencia p50/p95/p99;
- coste por consulta;
- tasa de fallback/abstención;
- calidad segmentada por tipo de pregunta.

## Variantes

- **Naive RAG:** recuperación directa + generación.
- **Hybrid RAG:** combina lexical y semantic retrieval.
- **RAG con re-ranking:** añade una segunda etapa de selección.
- **Graph RAG:** utiliza relaciones estructuradas para ampliar o seleccionar contexto.
- **Agentic RAG:** un agente decide cuándo, dónde y cómo recuperar información.
- **Corrective RAG:** evalúa la evidencia y repite la recuperación si la calidad es insuficiente.
